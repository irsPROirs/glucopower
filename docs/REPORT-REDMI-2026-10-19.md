# Сравнение Redmi и vivo по отчётам от 19 октября 2026

## Результат

На Redmi 8 с **GlucoPower 1.11** CC600 сам установил входящее BLE-соединение,
обнаружил пульсометр, включил уведомления и получил поток тестового ЧСС 93
на уровне обмена ATT: в HCI записаны **12 исходящих уведомлений `00 5D`**.
Это подтверждает рабочий путь от подписки до передачи пакетов контроллеру;
пользователь ранее также сообщил о показаниях ЧСС на CC600 с Redmi.

Для мощности самостоятельного соединения не появилось. При переключении
уже подключённого пульсометра на CPS компьютер **повторно обнаружил `1818`,
все три характеристики и CCCD**, но не включил уведомления и затем сам
отключился. Это существенно сужает исследование: регистрация CPS и его
обнаружение через GATT работают, однако выбор этого телефона как нового
BLE-мощемера на CC600 по-прежнему не подтверждён.

**Переход существующего HRS-соединения на CPS не обязывает приложение CC600
переклассифицировать сохранённый пульсометр в мощемер.** Повторное discovery
после Service Changed и отдельный поиск датчика мощности — разные проверки.
Из этой трассы нельзя заключить, что CC600 поддерживает мощность только по
ANT+, или что физическая совместимость уже исправлена.

## Реклама: одинаковые свойства при разных командах контроллеру

Redmi использует vendor-команду Android `LE_Multi_Advt`, opcode `0xFD54`.
Её формат описан в [AOSP HCI requirements](https://source.android.com/docs/core/connect/bluetooth/hci_requirements#multi-advertiser-support).
vivo использует стандартные Extended Advertising HCI-команды с включённым
legacy-режимом. Это разные способы настройки контроллера, а не разные
протоколы датчика в эфире: в обоих случаях настроена legacy-реклама.

| Свойство | Redmi, текущая запись | vivo, запись 01:41–01:51 |
| --- | --- | --- |
| Тип рекламы | `ADV_IND=0`: legacy, connectable, scannable, undirected | Event properties `0x0013`: те же свойства |
| PHY / каналы | LE 1M / 37, 38, 39 | LE 1M / 37, 38, 39 |
| Интервал min/max | 100 / 131,25 мс | 100 / 131,25 мс |
| Filter policy | 0, без фильтра списка разрешённых адресов | 0 |
| Own address | Random, RPA; новый при каждом новом сеансе рекламы | Random, RPA; новый при каждом новом сеансе рекламы |
| Flags | `02` | `02` |
| Appearance | Отсутствует | Отсутствует |
| Service UUID | `1818` либо `180D`, в ADV и scan response | То же |
| Имя | 7 байт; проверены ADV и scan response | 15 байт в ADV текущей записи; другое размещение проверялось ранее |
| TX power | Запрошено +1 dBm; фактический выбор не сообщается этим vendor-ответом | Запрошено +1, контроллер выбрал −1 dBm |
| Ответы настройки и запуска | Status 0 | Status 0 |
| Входящее соединение CC600 | Одно, в режиме HRS | Нет |
| Запись CCCD и уведомления HRS | Есть | Нет в этой текущей попытке |

Таким образом, **RPA, Flags `02` и отсутствие Appearance встречаются и в
успешном соединении Redmi → CC600**. Они не объясняют отказ vivo как общий
запрет этих параметров. Это не исключает различий конкретных контроллеров,
адресации или поведения CC600 в отдельных попытках.

## Работающее соединение ЧСС

В **02:14:49.374** получен успешный LE Enhanced Connection Complete.
Redmi играет роль **peripheral**, CC600 — central; адрес CC600 public,
интервал соединения 25 мс, latency 0, supervision timeout 6000 мс.
Исходящей команды Create Connection перед ним нет.

| Время МСК | Обмен |
| --- | --- |
| 02:14:49.573 | CC600 начинает поиск primary services |
| 02:14:49.800 | Телефон возвращает HRS `180D`, handles 147–150 |
| 02:14:51.101 | Обнаружена `2A37`, value handle 149, Notify |
| 02:14:51.299 | Обнаружен CCCD `2902`, handle 150 |
| 02:14:51.798–799 | MTU request 500, response 517, согласован MTU 500 |
| 02:14:53.023–756 | Шесть успешных чтений DIS Model Number `2A24` |
| 02:14:55.122 | CC600 пишет `01 00` в CCCD |
| 02:14:55.196 | Телефон отправляет Write Response |
| 02:14:55.206–02:15:06.057 | 12 уведомлений `00 5D`, тестовый ЧСС 93 |

Первое уведомление отправлено сразу после подписки, следующее через 644 мс,
дальнейшие — примерно раз в 1,02 секунды. Это непрерывная последовательность
пакетов, а не только запись устройства в списке датчиков. Retain-вызов
приложения выполняется после чтения его DIS и не создаёт новый физический
канал. Шифрование не требуется правами этих атрибутов и не включается в
наблюдаемом HRS-соединении.

## Смена профиля при живом соединении

В 02:15:06 приложение меняет `HEART_TEST` на `POWER_TEST`. Android освобождает
удержание канала приложением и закрывает его GATT-сервер, но **ACL остаётся
живым**. Новый сервер регистрируется на том же канале. Handle 149 меняет
назначение с HRS `2A37` на CPS `2A63`; сам по себе возврат из
`cancelConnection()` не подтверждает физическое отключение central.

Однако в этой попытке CC600 успешно обрабатывает изменение таблицы:

| Время МСК | Событие |
| --- | --- |
| 02:15:06.500 | Первая индикация Service Changed `2A05`, диапазон `0001–FFFF` |
| 02:15:06.572 | CC600 подтверждает её и заново запрашивает сервисы |
| 02:15:06.596; 06.748 | Вторая индикация Service Changed и подтверждение |
| 02:15:06.848 | Ответ содержит CPS `1818`, handles 147–154 |
| 02:15:07.901 | Получены `2A63` Notify, `2A65` Read, `2A5D` Read |
| 02:15:08.101 | Обнаружен CCCD `2902`, handle 150 |
| 02:15:08.526 | Перечисление атрибутов закончено |
| 02:15:14.359 | Удалённая сторона завершает соединение, reason `0x13` |

После смены профиля CC600 не читает Feature или Location, не пишет CCCD
и не получает уведомлений мощности. Исходящей HCI Disconnect перед
завершением нет. Все ATT Error Response в файле имеют код `0x0A` при окончании
перечисления; ошибок аутентификации, авторизации или размера ключа нет.

Следовательно, причиной этой конкретной попытки нельзя объявить отсутствие
CPS в таблице, отсутствие дескриптора или отсутствие повторного discovery.
Внутренняя логика выбора типа датчика CC600 остаётся ненаблюдаемой. Даже
корректно обнаружив CPS на старом HRS-канале, компьютер может продолжать
обрабатывать его как соединение пульсометра.

## Что сравнение исключает и что остаётся неизвестным

* Общий запрет BLE Peripheral или уведомлений в Android 16 исключён рабочим
  сценарием Redmi. Убийство foreground service в этих записях не наблюдается.
* Старая таблица CC600 не объясняет отказ после указанного Service Changed:
  повторный обход CPS подтверждён трассой.
* Системные предупреждения Redmi `server not opened` при удалении сервиса и
  AIS/L2CAP при обработке MTU встречаются до успешного HR. Их наличие само по
  себе не доказывает причину отказа CPS.
* В Java GATT Server Map Redmi присутствует один сервер приложения, vivo —
  семь, с дополнительными системными и OEM-сервисами. Это не полная native
  GATT-база и не доказательство лимита памяти CC600.
* Для vivo не установлена причина отсутствия входящего CC600-соединения.
  Для CPS на обоих телефонах не установлена причина отсутствия выбора
  датчика и подписки. Это отдельные вопросы; рабочая ЧСС на Redmi не
  доказывает поддержку любой реализации CPS данной прошивкой CC600.

Без эталонной успешной попытки менять Feature, добавлять Control Point,
каденс, нестандартные рекламные поля или расширять очередь уведомлений
ради этих отказов не обосновано. Последняя очередь в сценарии ЧСС уже
доставляет пакеты после действительной подписки.

## Следующий эксперимент

Нужен **независимый CPS-сервер nRF Connect на том же Redmi**, который уже
прошёл проверку ЧСС. Это позволит сравнить реализации при одинаковом телефоне
и контроллере. Подробная конфигурация и макрос 93 Вт:
[проверка через nRF Connect](NRF-CONNECT-CPS-TEST.md).

1. Остановить GlucoPower. В nRF Connect настроить единственный фитнес-сервис
   CPS `1818`: `2A63` Notify с одним CCCD, `2A65` Read = `00 00 00 00`,
   `2A5D` Read = `05`. Запустить connectable legacy-рекламу с `1818` в ADV.
2. На CC600 удалить **только старую запись этого Redmi как датчика** и
   запустить новый поиск мощности. Оставить CPS включённым не менее 60 секунд;
   в этой попытке не переключать телефон в HRS.
3. Если датчик добавлен и CCCD включён, отправлять `00 00 5D 00` раз в секунду
   и проверить число 93 в поле мощности CC600. Записать время и результат.
4. Сохранить серверный журнал и системную HCI-трассу. При успехе сравнить
   ADV, роли, порядок GATT discovery и ответы ATT с GlucoPower на Redmi.

Успех независимого сервера даст конкретный образец для исправления приложения.
Неуспех не докажет ANT-only и не выделит автоматически виновную сторону:
тогда потребуется подтверждение поддержки BLE CPS производителем CC600
для этой прошивки либо проверка с заведомо работающим BLE-мощемером.
