# Трасса vivo → CC600 для GlucoPower

Нужен системный HCI-журнал одной попытки. Новый APK для этого не требуется.
Журнал приложения от 01:03:35 показывает рекламу обоих профилей, но ни одного
обращения CC600. Единственный LINK относится к другому устройству.

## Подготовка на vivo

1. Включить параметры разработчика, если они ещё не включены. Названия пунктов
   зависят от прошивки vivo.
2. В параметрах разработчика включить **Bluetooth HCI snoop log / Журнал Bluetooth
   HCI**. Если есть выбор режима, выбрать полный журнал, а не фильтрованный.
3. Выключить и снова включить Bluetooth. Это кратковременно разорвёт текущие
   Bluetooth-соединения. AOSP требует перезапуска Bluetooth, чтобы настройка
   журналирования вступила в силу.
4. Запустить текущую версию GlucoPower и выбрать **тест мощности 93 Вт**. До окончания
   попытки не переключаться на ЧСС. Не подключать nRF Connect к vivo.
5. На CC600 удалить старую запись телефона из датчиков, запустить новый поиск
   мощности и записать точное время начала. Если датчик найден, добавить его и
   открыть страницу поездки с мощностью. Подождать 60 секунд, записать результат
   и скопировать диагностику GlucoPower.
6. Сразу собрать системный отчёт одним из способов ниже. После сбора отключить
   HCI-журналирование, когда оно больше не нужно.

Официальный порядок включения и перезапуска: [AOSP — Debugging with logs](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging#debugging-with-logs).

## С компьютером Windows

Подключить vivo по USB, включить **отладку по USB** и подтвердить доступ этому
компьютеру на телефоне. В PowerShell из папки проекта выполнить:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\collect-ble-diagnostics.ps1
```

Скрипт использует ADB из `.tools/android-sdk/platform-tools` либо из PATH.
При нескольких телефонах требуется `-Serial`; свой путь к ADB можно передать
через `-AdbPath`. Скрипт читает состояние Bluetooth, журнал приложения и создаёт
`adb bugreport`. Он не переключает Bluetooth, не меняет сопряжения, не очищает
журналы и ничего не отправляет в сеть. Отчёт создаётся несколько минут.

Результат находится в `diagnostics/<дата-время>/`. Скрипт распознаёт заголовок
`btsnoop`, включая стандартные `btsnoop_hci.log` и файлы vivo `bt_hci_*.cfa`.
Они отдельно извлекаются как `hci-1-btsnoop.log` и т. п.;
`hci-files.txt` содержит исходные имена. Для разбора нужны эти HCI-файлы, время
попытки и диагностика GlucoPower. `bugreport.zip` остаётся локально: он может
содержать данные других приложений и не требуется целиком при наличии трассы.

Уже собранный архив можно обработать **без телефона и повторного bugreport**:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\expand-ble-traces.ps1 -BugreportPath .\diagnostics\20261019-014842-222\bugreport.zip
```

На vivo V2547A в отчёте от 19.10.2026 обнаружены полноценные файлы btsnoop H4
с расширением `.cfa`. Предупреждение старого сборщика «No raw btsnoop_hci.log»
оказалось следствием фильтра имени. Пустой результат `getprop
persist.bluetooth.btsnooplogmode` тоже не доказывает выключенное журналирование:
в этом отчёте системный журнал содержит отказ доступа к свойству. Разбор самой
попытки — [REPORT-VIVO-2026-10-19.md](REPORT-VIVO-2026-10-19.md).

## Без USB и компьютера

В параметрах разработчика выбрать **Создать отчёт об ошибке / Take bug report**
и дождаться уведомления о готовности. Сохранить ZIP в файлы телефона. Название
и наличие пункта зависят от vivo. Стандартные HCI-файлы могут находиться внутри
`FS/data/misc/bluetooth/logs/`; наличие их в отчёте зависит от прошивки. Само
приложение GlucoPower не имеет доступа к этим системным файлам.

Способы получения и устройство ZIP: [Android — Capture and read bug reports](https://developer.android.com/studio/debug/bug-report).

## Что проверять в трассе

* HCI-параметры рекламы, рекламные данные и scan response, ответы контроллера.
  Принятие HCI-команды ещё не доказывает приём рекламы компьютером в эфире.
* Наличие LE Connection Complete / Enhanced Connection Complete, адреса и роли
  соединения, его ошибки или последующий Disconnect.
* При наличии соединения — ATT discovery, чтения характеристик, запись `01 00`
  в CCCD и Handle Value Notification. Discovery может не попадать в журнал
  приложения, поскольку его обрабатывает системный стек.

Без соединения трасса vivo не покажет причину решения CC600 не подключаться.
Для проверки приёма рекламы самим CC600 может потребоваться внешняя BLE-трасса
или журнал его прошивки. Если сырой HCI-файл отсутствует, из текстового bugreport
иногда можно получить ограниченный BTSNOOZ через официальный `btsnooz.py`.
Он не гарантирует полноту ATT-данных и не заменяет полный snoop. См.
[AOSP — Debugging with bug reports](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging#debugging-with-bug-reports).
