# ArduinoBLE, you-gatt-me и вариант Gemini

Проверено 19 октября 2026 года. Это сравнение исходников, а не подтверждение
совместимости GEOID CC600. Исходные файлы Gemini не заменяют код приложения.

## ArduinoBLE-Cycle-Power-Service

[Снимок исходника](https://github.com/Tschucker/ArduinoBLE-Cycle-Power-Service/blob/8632eef2393cb4a8abcd198c9955cdf0fc657191/blecyclepower/blecyclepower.ino),
MIT. Платформа — Arduino Nano 33 BLE Sense, а не Android.

* Primary CPS `1818`, Feature `2A65`, Measurement `2A63`, Location `2A5D`;
  сервис указан в рекламе, Control Point отсутствует.
* Measurement имеет Read/Notify и восемь байт: Flags `0x0020`, мощность,
  счётчик оборотов шатуна и время последнего оборота в единицах 1/1024 с.
  Обороты здесь вычисляются из магнитометра, а не выдумываются ради подключения.
* Location `0x0D` — Rear Hub. Это выбор конкретного датчика, не универсальное
  требование для распознавания мощности.
* Feature записан как `00 00 00 08`: при little endian это `0x08000000`,
  а не ожидаемый Crank Revolution Data Supported `0x00000008` (`08 00 00 00`).
  Не переносить эту ошибку или вычисления мощности магнитометра в GlucoPower.
* Значения Feature/Location записываются внутри обработки события магнитометра,
  уже после начала рекламы. В GlucoPower read-ответы должны быть готовы сразу.

Полезно: сверка порядка байтов Measurement, UUID и отделение рекламы от
передачи после подключения. Не доказывает обязательность каденса, Read у
Measurement или конкретной Location для CC600.

## you-gatt-me

[Снимок репозитория](https://github.com/tobias74/you-gatt-me/tree/9f4770d0dcce7f5feda7133af2199a1c6ebc0a49),
MIT. Проверены ApplicationState, GattProfile, CyclingPowerProfile,
CylcingPowerMeasurementCharacteristic, AbstractDataMeasurementCharacteristic
и ClientConfigDescriptor.

* Разделяет профили, характеристики, данные и подписчиков по устройствам.
* Реклама connectable, UUID в ADV, имя только в scan response, режим BALANCED,
  TX MEDIUM. Это доступный вариант сравнительного эксперимента, не доказанное
  исправление vivo. В GlucoPower 1.12 сравнивается только состав пакетов;
  интервал и TX оставлены прежними, чтобы не менять несколько условий сразу.
* Уведомления идут подписавшимся устройствам раз в секунду. CCCD read зависит
  от клиента; запись `01 00` включает уведомления.
* CPS публикует только Measurement: обязательные Feature и Sensor Location
  отсутствуют. При Flags=0 выделяется 14 байт, хотя определены только первые
  четыре. Не копировать лишние десять байт.
* UUID сопоставляются через Kotlin `===` (идентичность объекта), что не равно
  сравнению UUID по значению. В GlucoPower используется `==`.
* Реклама запускается до регистрации GATT; нет последовательного ожидания
  onServiceAdded. CCCD не проверяет все offset/prepared-write варианты;
  отправка использует старый API и не ожидает onNotificationSent.

Полезно: структура профилей и простой вариант ADV. Этот симулятор не является
эталоном полного CPS или устойчивой фоновой службы Android 16/17.

## Почему вариант Gemini не применён целиком

Во вложении `1-GlucoBleBridgeService.kt.txt` обнаружены следующие изменения:

| Изменение | Решение |
| --- | --- |
| Проверка `Build.FINGERPRINT != "robolectric"` меняет формат пакета и рекламу | Отклонено: тесты должны проверять ту же логику, что телефон |
| Освобождение pending через 1,5 с без onNotificationSent | Отклонено: поздний callback может подтвердить уже другой пакет |
| Искусственные 60 RPM в режиме глюкозы | Отклонено: нет измеренных оборотов; это может вмешаться в настоящий каденс |
| Control Point и Success на произвольный opcode | Отклонено: не реализует процедуры, длины и результаты CPS; может ложным образом подтвердить калибровку |
| Любые ненулевые два байта принимаются как подписка Control Point | Отклонено: значения CCCD должны соответствовать свойствам характеристики |
| Ответы из Binder-потока с последующим изменением состояния на main | Заменено одним последовательным BLE-потоком; нет доказанного требования Android 17 отвечать именно в Binder-потоке |
| UUID только в ADV | Добавлено как явно выбираемый диагностический вариант, одинаковый в тестах и на телефоне |

Ни Arduino, ни you-gatt-me не подтверждают комментарий Gemini о том, что CC600
обязательно требует `2A66`. При текущих нулевых Feature GlucoPower Control Point
не добавляется. См. [CPS, §3.4](https://www.bluetooth.org/DocMan/handlers/DownloadDoc.ashx?doc_id=585857).

## Android 17 и результаты устройств

Пользователь сообщил обновление vivo до Android 17, но ещё не проверял 1.11.
Новая прошивка/API и результат приёма ожидаются. Трассы 01:48 и 02:16 относятся
к Android 16 (vivo и Redmi соответственно). Android 10 в donor fingerprint
Redmi не является версией его работающей LineageOS: runtime — Android 16.

Android 17 (API 37) добавляет автоматическую попытку восстановления потерянного
bond. KEY_MISSING приходит после неуспеха такого восстановления. Это не доказывает
исправление обнаружения CPS и не заменяет проверку CCCD. Loopback внутри одного
профиля Android сохраняется; HTTP между разными пользовательскими профилями
ограничен. GlucoPower и источник для локального HTTP должны быть в одном профиле.
Источник: [изменения для всех приложений Android 17](https://developer.android.com/about/versions/17/behavior-changes-all).

Факты предыдущих устройств: [vivo](REPORT-VIVO-2026-10-19.md),
[Redmi](REPORT-REDMI-2026-10-19.md). Нельзя переносить выводы об Android 16 на
новую прошивку без новой попытки. Изменение очереди уведомлений не объясняет
отсутствие входящего соединения, а повторное discovery CPS на HR-соединении
не обязывает CC600 переклассифицировать сохранённый пульсометр в мощемер.
