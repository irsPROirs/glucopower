# Разбор системного отчёта vivo от 19 октября 2026

## Вывод для GlucoPower 1.11

В записанной попытке контроллер vivo принял корректную legacy-рекламу CPS
`0x1818`, но входящее LE-соединение с CC600 не завершилось ни разу. Для ЧСС
`0x180D` результат тот же. Поэтому в этой попытке отсутствие данных возникает
до подписки CCCD и до отправки измерений. Это уточняет место отказа, но ещё
не устанавливает причину решения/неудачи подключения на стороне CC600.

Пользователь подтвердил, что на CC600 был открыт **поиск всех доступных
датчиков**: мощность не обнаружена, ЧСС сохранена в списке, показаний нет.
Сохранение записи по рекламе не равнозначно установленному LE/GATT-соединению.
Исправление совместимости и передачи vivo → CC600 пока не подтверждено.

## Материалы и полнота

Локальный архив: `diagnostics/20261019-014842-222/bugreport.zip`.
Устройство: vivo V2547A, Android 16, прошивка
`PD2547E_A_16.0.22.14.W10`. В архиве оказались **10 файлов HCI** с именами
`FS/data/misc/bluetooth/logs/bt_hci_*.cfa`. Расширение нестандартное, содержимое —
обычный **btsnoop version 1, datalink 1002 (H4)**. Формат заголовка сверяется с
[Wireshark btsnoop reader](https://github.com/wireshark/wireshark/blob/master/wiretap/btsnoop.c).

Текущая трасса `bt_hci_20261019_014147_d.cfa`:

* 5 999 710 байт; 21 875 записей;
* SHA-256 `b4adf8c50c4c3f4a0fb273b6a4b35aedbb2c4267282afa3f6419af363b9b3f42`;
* интервал по сопоставлению с журналом телефона: **01:41:47.644–01:51:29.214**;
* нет усечённых записей или ошибок границ; поле счётчика потерь равно нулю.

В этой прошивке времена внутри btsnoop совпадают с местными часами logcat при
декодировании как UTC. Для сопоставления использована явная поправка −3 часа
с отображением +03:00. Она специфична для этой записи; на Redmi её нужно
проверить заново. Нулевой счётчик потерь характеризует файл, а не приём пакетов
в радиоэфире.

Сырые файлы остаются в игнорируемой Git папке `diagnostics/`. В документацию
не переносятся Bluetooth-адреса, ключи и данные других приложений.

## Что контроллер действительно получил

GlucoPower использует advertising handle 1; параллельная системная реклама vivo
имеет handle 0. Для handle 1 в HCI подтверждены:

| Поле | Значение |
| --- | --- |
| Advertising event properties | `0x0013`: legacy, connectable, scannable, undirected |
| Primary PHY | LE 1M |
| Интервал min/max | 100–131,25 мс |
| Каналы | 37, 38, 39 |
| Filter policy | 0: допускаются scan/connection requests от любых устройств |
| Own address type | Random; адрес имеет формат RPA |
| Запрошенная / выбранная контроллером TX power | +1 / −1 dBm |
| Основной ADV | 24 байта: Flags `02`, Complete Local Name (15 байт), Complete 16-bit UUID List |
| Scan response | 4 байта: Complete 16-bit UUID List |
| UUID в режиме мощности | `1818` в обоих пакетах |
| UUID в режиме ЧСС | `180D` в обоих пакетах |
| Ответы на команды настройки/запуска рекламы | `Command Complete status=0` |

UUID мощности реально присутствует в переданных контроллеру данных, а не
только в строке приложения. Extended **HCI-команды** здесь программируют
**legacy-пакеты**; само слово Extended в названии команды не означает
несовместимую extended-рекламу в эфире.

| Время телефона | Режим / событие |
| --- | --- |
| 01:42:01 | Запущена реклама `180D` |
| 01:44:27–01:48:00 | Непрерывный сеанс `POWER_TEST`, реклама `1818` более трёх минут |
| 01:48:01 | Переход на `180D` |
| 01:48:27–01:48:28 | Короткий повторный сеанс `1818` |
| 01:48:29 | Возврат к `180D`, продолжение до конца записи |

При каждом новом запуске рекламного набора Android назначает **другой RPA**.
Внутри длинного сеанса мощности смены адреса не зафиксировано. После 01:48:29
до конца файла адрес handle 1 тоже не менялся. Краткое системное выключение
обоих наборов в 01:50:31 длится около 3 мс и завершается успешным включением.

Смена адреса при переключениях — подтверждённый факт. Ошибка обработки RPA
или сохранённого адреса в CC600 — пока гипотеза. В публичном Android API нет
обычного setter для произвольного адреса или исключения чужих сервисов из
общей GATT-базы. Перегрузка изоляции GATT в AOSP помечена `@SystemApi`/`@hide`
и имеет требования `BLUETOOTH_PRIVILEGED`; это не доступное обычному APK
исправление. См. [API рекламы](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser),
[публичные параметры](https://developer.android.com/reference/android/bluetooth/le/AdvertisingSetParameters.Builder),
[AOSP: изолированный GATT](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/framework/java/android/bluetooth/le/BluetoothLeAdvertiser.java#493).

## Соединения и состояние приложения

В текущем HCI есть три успешных новых LE-соединения: 01:41:52.517,
01:45:27.908 и 01:46:05.296. Во всех vivo играет роль **central**, удалённое
устройство одно и то же — Ottai. Это согласуется с `com.ottai.seas` в GATT
Client Map и временем LINK/ACL в журнале GlucoPower.

Ни одного `LE Connection Complete`/`Enhanced Connection Complete` с локальной
ролью **peripheral** нет. CC600 в новых соединениях этой трассы отсутствует.
Нет discovery локальных CPS/HRS, записи CCCD или уведомлений этих профилей.
Служебный ATT другого соединения не является подпиской CC600.

`dumpsys activity services` подтверждает, что GlucoPower жив:
`isForeground=true`, тип `connectedDevice` (`0x10`), `startRequested=true`.
Bluetooth зарегистрировал сервер и оба обязательных CPS read-атрибута с
обычными правами; CCCD имеет READ/WRITE без обязательного шифрования.
Таким образом, эта попытка не показывает убийство foreground service,
отсутствие разрешения рекламы или отказ регистрации сервиса.

Системный отчёт показывает ёмкость Resolving List **32**, а текущая трасса —
три команды добавления записей в него. Число сохранённых сопряжений телефона
не доказывает заполнение списка; массовое удаление сопряжений не обосновано.

## Что дополнительно видно в старой попытке 1.9

Архив содержит также HCI предыдущих сеансов. В записи около **00:52:25**
ручной `GATT ATTACH` действительно создал LE-канал: vivo — **central**.
Но CC600 после этого выступил **GATT-клиентом телефона**. Роли GAP и GATT
независимы; нельзя утверждать, что исходящее соединение автоматически сделало
CC600 только GATT-сервером для приложения синхронизации.

CC600 прошёл discovery и получил обязательные элементы HRS:

| Время | Обмен |
| --- | --- |
| 00:52:27.120 | Ответ телефона содержит HRS `180D`, диапазон handles 190–193 |
| 00:52:35.279–35.280 | Запрос `Read By Type 2803`; ответ: `2A37`, value handle 192, properties `0x10` (Notify) |
| 00:52:35.579–35.580 | `Find Information` на handle 193; ответ: CCCD `2902` |
| 00:52:36.124 | Завершение обхода последнего сервиса DIS |
| 00:52:36.239–36.241 | Обмен MTU 500 |

После этого CCCD не записан. В обмене есть обычные `Attribute Not Found (0x0A)`
при окончании перечисления атрибутов; их нельзя трактовать как ошибку
аутентификации. Недостаточный MTU и отсутствие CCCD эту попытку не объясняют.
Большая общая GATT-база телефона присутствует, но сам факт успешного обхода
не доказывает лимит памяти или ошибку парсера CC600.

Шифрование этого канала в **00:52:26.410** завершилось с `status=0`,
`enabled=1`, размером ключа 16 байт. Гипотеза сбоя шифрования именно этой
попытки не подтверждается. По всем десяти файлам найдены ещё два завершённых
соединения с тем же известным CC600 — 00:12:25.125 и 00:13:04.206; там также
vivo — central и шифрование успешно. Завершённых соединений с ролью
vivo-peripheral для этого CC600 не найдено, хотя с другими устройствами
такие события есть. Это вывод по наблюдаемому адресу CC600 и событиям файлов;
он не исключает старые соединения вне записанного интервала или неизвестный
адрес другого сеанса.

Таким образом, есть **два разных наблюдения**: старое принудительное соединение
дошло до discovery без подписки; новая попытка обычного поиска не дошла до
завершённого входящего соединения. Их нельзя смешивать в один подтверждённый
сценарий «шифрование сломалось» или «notify не работает».

## Изменения по результату разбора

* Сборщик распознаёт btsnoop по заголовку, включая vivo `.cfa`, и сохраняет
  соответствие исходных имён. Повторно собирать этот архив не нужно.
* Извлечение вынесено в `tools/expand-ble-traces.ps1`, работает без ADB.
  Проверены стандартные и OEM-имена, ложные/короткие заголовки, сохранность
  существующих файлов и безопасные имена назначения.
* Для будущего logcat сборщик явно декодирует вывод ADB как UTF-8.
  Полный bugreport уже содержит читаемый русский журнал текущей попытки.
* Добавлен `tools/read-vivo-hci.py` для локального разбора рекламы, ролей и ATT
  без вывода ключей и произвольного содержимого ACL. Enhanced ATT не разбирается;
  для подробного анализа можно открыть извлечённый btsnoop в Wireshark.

Проверка инструментов: **10 автоматических тестов пройдены** (3 для извлечения
и 7 для HCI/ATT-парсера), `git diff --check` без ошибок. Эти тесты выполняются
без телефона; они проверяют разбор файлов, а не совместимость CC600.

```powershell
python -m unittest discover -s tools -p 'test_*.py' -v
python tools/read-vivo-hci.py diagnostics/20261019-014842-222/traces/hci-8-btsnoop.log --timestamp-correction-hours -3 --display-offset-hours 3 --output diagnostics/20261019-014842-222/analysis/hci-current-summary.json
```

Новый APK по этой трассе не создан: изменения UUID, значений мощности, MTU или
очереди уведомлений не устраняют установленное отсутствие входящего соединения.

## Следующий сравнительный эксперимент

Нужна такая же HCI-запись **Redmi 8 с той же версией 1.11**:

1. Включить полный HCI-журнал, перезапустить Bluetooth.
2. Оставить только Redmi подключённым к компьютеру по USB.
3. Проверить `HEART_TEST` 93 на CC600, дождаться появления числа на экране;
   записать время и результат. Затем проверить `POWER_TEST` не менее 60 секунд.
4. Собрать один отчёт уже исправленным `collect-ble-diagnostics.ps1`.

Сравнение покажет адрес и его тип, структуру ADV, фактическую роль соединения,
GATT discovery и запись CCCD в работающем сценарии. Если на Redmi снова
работает ЧСС, но не мощность, отказы нужно исследовать раздельно. Причину
фильтрации CPS самим CC600 нельзя вывести из телефонного HCI, если CC600
вообще не инициирует соединение; для неё может потребоваться трасса эфира
или подтверждение производителя по поддержке BLE CPS конкретной прошивкой.
